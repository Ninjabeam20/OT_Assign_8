# Systems tracks F and G

## F: compiler and pass ordering

`optlab/track_f.py` implements tokenization, recursive-descent parsing, immutable temporary-based IR, an interpreter, and C emission. The language has `let`, reassignment, parentheses, addition/subtraction/multiplication and `return`. Values are unsigned 64-bit integers; all operations wrap modulo 2^64. Undefined variables and trailing statements are errors. There is no control flow or division.

Four independently selectable passes implement constant folding, copy/constant propagation, liveness-based dead code elimination, and common subexpression elimination (including commutative normalization). Tests enumerate all 24 pass permutations on precedence, reassignment, redundancy, and overflow cases. Native checks compile baseline and chosen IR through Clang `-O0`, compare output checksums, and check interpreter edge inputs.

Optimization: minimize weighted IR cost, with multiply costing 3 and other instructions 1. Each greedy iteration evaluates 64 ordered triples of the four passes and accepts only a strict cost decrease, stopping at a local optimum or 12 rounds. This is a discrete black-box optimization formulation with correctness constraints; it is not a proof of globally optimal ordering. Two-pass lookahead initially became stuck on the constant chain; a failing regression led to three-pass lookahead.

`results/F.json` records five native CPU-time samples per variant, median runtime, native static function instruction count from `otool`, generated C source bytes, executable bytes, compilation time, chosen order, search trace, and checksums. Executable sizes include fixed Mach-O padding and may not shrink even when instruction count does. Static instruction count is not hardware retired instructions. Compilation time has one sample per variant and should not be interpreted as a stable improvement. `frontend_seconds` measures parsing; `search_seconds` measures all greedy candidate evaluation; `backend_compile_seconds` measures C generation, source writing and clang execution. Baseline end-to-end compilation sums frontend and backend; optimized end-to-end adds search. The legacy `compile_seconds` field is explicitly clang-only. Full runs use 100 million input values, quick runs 100,000.

## G: real xv6, COW and lottery scheduling

Source is MIT's official xv6-riscv, pinned at `4ded343d5d9d40d4e9dcf4867ca45b14170bf364`. `scripts/xv6-upstream.json` records provenance and the exact archive SHA-256; both vendored source trees retain MIT's license. The exact commit archive's kernel files were compared byte-for-byte to the baseline. Both variants have the same added `user/optbench.c` and Makefile entry. `scripts/xv6-optimization.patch` contains only the actual kernel optimization delta.

Baseline uses upstream eager fork copying and round-robin scheduling. Optimized kernel uses equal-ticket lottery scheduling (one ticket per runnable process, per-hart xorshift state) and copy-on-write fork. Writable pages receive a software COW PTE bit, are shared with reference counts, and are copied on store faults. Kernel `copyout` resolves COW too; read-only text and guard pages remain protected. Reference counts are lock protected. The common upstream lazy allocation behavior remains supported.

The implementation follows the [MIT COW lab](https://pdos.csail.mit.edu/6.1810/2024/labs/cow.html) and builds the [actual MIT kernel](https://github.com/mit-pdos/xv6-riscv). It is not a scheduling simulator. Homebrew `qemu` and `riscv64-elf-gcc` provide execution and compilation. Host compiler builds mkfs. `optlab.track_g.guest` launches QEMU with 128 MiB RAM, default one hart, boots the shell, runs workloads, and runs the entire upstream `usertests` command including slow tests. Timeouts, panics, missing metrics, and guest correctness failures raise errors rather than becoming fabricated results.

Workloads: fork touches 16 MiB then creates 200 children, checking private writes and parent isolation; CPU runs four compute-bound children; mixed runs four compute/sleep children for 20 rounds. A pipe read into COW memory checks kernel copyout. All children are waited for and statuses checked. Guest `uptime` measures elapsed timer ticks. Full measurements have three repetitions per kernel. CPU and fork workloads were expanded after initial experiments found zero-tick CPU timings; preliminary results are not reported as final speedups. Three-hart execution additionally exercises synchronization.

Performance limitations: virtualized QEMU results are host-dependent; equal tickets do not model configurable priorities; coarse timer ticks limit small effects. Lottery is not expected to systematically improve aggregate CPU throughput. The paired kernel change combines COW and scheduling, so attribution requires future ablation; fork improvement plausibly comes primarily from avoided copying. No hardware performance counters are claimed.

## Reproduction and evidence

From a fresh clone, run `.venv/bin/python scripts/xv6-setup.py` to fetch the pinned archive, verify its SHA-256, add the shared guest workload, and apply the kernel patch. This setup was exercised in a separate temporary directory and its optimized vm.c matched the measured tree. It refuses to overwrite existing xv6 directories. From the project directory, use `.venv/bin/python -m pytest tests/test_systems.py -q`. Call `optlab.track_f.run()` or `optlab.track_g.run()` and serialize the returned dictionary. G requires the installed `qemu-system-riscv64`, `riscv64-elf-gcc`, binutils and make. `scripts/xv6-verify.py` runs G and saves JSON. Logs in `results/xv6/` include build commands, full guest tests and measurements. Prompts and observed failures live in `prompts/F/` and `prompts/G/`.

Observed setup failures: direct git clone timed out on TLS, so official codeload plus exact-commit verification was used. Initial project pytest/pexpect imports failed while parent dependency installation was pending; the QEMU runner uses standard-library subprocess/selectors and requires no pexpect. GCC's kernel RWX load-segment warning is inherited from the upstream linker script. Upstream negative usertests deliberately print page faults, allocation exhaustion, and file-system exhaustion; only the final `ALL TESTS PASSED` indicates success.

Validation completed: full upstream usertests passed on baseline (one hart), optimized (one hart), and optimized (three harts). Final timing runs are sequential, with correctness logs retained separately from timing logs.

Final observed results (this host): F median native speedups were approximately 1.62x, 1.55x and 1.60x across the three programs; static native function instructions fell 19→9, 25→12 and 35→15. G median fork ticks fell 81→8 (10.125x), while CPU remained 13→13 and mixed remained 20→20. These are measured workload results, not a claim that lottery scheduling improves throughput. Raw samples and exact values are in the JSON files.

Runner hardening after initial measurements: full `run()` now includes optimized three-hart full usertests automatically (quick mode omits that additional SMP boot). Every guest invocation gets a unique log directory, separate timing/verification/build logs, relative artifact paths, explicit repetitions and verification scope, and a freshly regenerated filesystem. Zero-duration ratios raise an error asking for longer workloads; no denominator clipping is used. A real workload boot and a focused three-hart upstream `copyout` test verified these changes; all original full-suite logs and reported timing values are retained. The final full runner execution completed in about 446 seconds, regenerating measurements and all three complete usertest validations using the hardened protocol; consult G.json metadata for the exact timestamp and duration. Lottery fairness has not been measured, and no fairness improvement is claimed.
